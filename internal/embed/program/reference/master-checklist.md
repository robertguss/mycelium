# Master Completion Checklist

A Research Program Architect should not declare the workflow configured until
all applicable items are true.

## Governance

- [ ] Git is the durable system of record
- [ ] Repository follows the standard layout
- [ ] `research-program.toml` exists and validates
- [ ] Fresh sessions are mandatory
- [ ] Human approval gates are defined
- [ ] Rigor tier is approved
- [ ] Authority and precedence are explicit
- [ ] Identifier ranges are allocated

## Discovery and program design

- [ ] User interviewed one question at a time
- [ ] Recommendations accompanied clarification questions
- [ ] Underlying goal separated from proposed solution
- [ ] Material pivots received explicit approval
- [ ] Program Blueprint accepted
- [ ] Research Charter accepted
- [ ] Adaptive research graph explicit
- [ ] Stage dependencies and parallel groups explicit
- [ ] Obvious omitted tracks justified

## Evidence

- [ ] Source hierarchy defined
- [ ] Current claims require verification
- [ ] Portable citations required
- [ ] Evidence Ledgers mandatory
- [ ] Evidence spikes first-class
- [ ] Spike reports bounded and reproducible
- [ ] Weak and conflicting evidence disclosed
- [ ] Optional replication supported
- [ ] Replication uses independent fresh sessions
- [ ] Reconciliation preserves dissent and original reports

## Stage execution

- [ ] Prompts generated just in time
- [ ] Every stage has an attachment manifest
- [ ] Every substantive stage runs in a fresh session
- [ ] Every artifact is standalone
- [ ] Every report contains a Handoff Digest
- [ ] Every stage has a completion checklist
- [ ] Every artifact passes independent validation
- [ ] Only validated committed artifacts unlock downstream stages

## Synthesis and review

- [ ] Every recommendation dispositioned
- [ ] One coherent specification produced
- [ ] Normative requirements use stable identifiers
- [ ] Specification receives adversarial review
- [ ] Findings contain concrete failure scenarios and corrections
- [ ] Every finding dispositioned in revision
- [ ] Revised specification has honest implementation status
- [ ] Additional review rounds risk-triggered only

## Implementation planning

- [ ] Plan subordinate to accepted specification
- [ ] Plan organized into phases and milestones
- [ ] Plan does not become a task backlog
- [ ] Every phase has entry and exit criteria
- [ ] Evidence spikes before irreversible commitments
- [ ] Integration and dogfooding begin early
- [ ] Plan receives adversarial review
- [ ] Every plan-review finding dispositioned
- [ ] Final revised plan has honest delivery status

## Closure

- [ ] Requirement-to-phase traceability complete
- [ ] Risks and open questions have owners and deadlines
- [ ] Manifest records accepted commit hashes
- [ ] Working tree clean
- [ ] Final implementation handoff actionable
- [ ] No substantive implementation without accepted authority
